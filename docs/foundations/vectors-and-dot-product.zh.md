# 向量与点乘

!!! abstract "这一页回答什么"
    为什么光照写成 `dot(N, L)`、这个数到底是什么意思，以及游戏里点乘真正在干活的四个地方。
    十分钟。

## 一个向量同时是两样东西

同样三个数，既可以表示**位置**，也可以表示**方向**，引擎对两者的处理几乎一样。都是 `Vector3`：

```csharp
Vector3 position = transform.position;    // 东西在哪
Vector3 forward  = transform.forward;     // 东西朝哪
```

差别在于你被允许对它做什么：

- 两个**位置**相减，得到方向：`target - self` 就是从你指向目标。
- 一个位置加一个方向，得到新位置。
- 两个**方向**可以互相比较 —— 同向、反向、还是成直角？这就是点乘，也是这一页存在的理由。
- 两个位置不能这样比较。「苏州和上海有多像」不是一个问题。

## 长度与归一化

向量的长度（模）是从原点到它尖端的距离：

```text
|v| = sqrt(vx*vx + vy*vy + vz*vz)
```

**归一化**（单位化）之后的向量长度正好是 1。它保留方向、丢掉长度。Unity 里是
`v.normalized`，着色器里是 `normalize(v)`。

所有需要「角度」或「朝哪边」的答案，都需要单位向量。如果你把长度是 3 的向量喂给点乘，结果会
大 3 倍 —— 而且看起来照样像对的，所以这个 bug 能活很久。

## 加法与缩放

```text
新位置 = 位置 + 方向 * 速度 * deltaTime
```

方向乘正数只是变长、不转向；乘负数就掉头。速度作用到位置上就是这么来的，这也是为什么多数移动
代码把**速度大小**和**方向**分开存。

两个方向相加没有明确意义；两个**速度**相加有：玩家自己的移动加上一阵风，是新的速度。

## 点乘

点乘吃两个向量，吐一个数：

```text
a · b = |a| * |b| * cos(theta)
```

`theta` 是两者之间的夹角。如果两个向量都是单位长度，长度项消失，点乘**就是**夹角的余弦：

| 两者夹角 | 点乘（单位向量） | 含义 |
| --- | --- | --- |
| 0° | 1 | 完全同向 |
| 60° | 0.5 | 大致同向 |
| 90° | 0 | 垂直 |
| 120° | -0.5 | 大致反向 |
| 180° | -1 | 完全反向 |

所以点乘是两个方向之间的**相似度分数**，取值范围天然被限制在 −1 到 1。就这么简单。它到处都是，
是因为「A 方向和 B 方向有多一致」是游戏里不停在问的问题。

## 符号告诉你的事

对两个单位方向：

- `dot > 0` —— 同向。翻成玩法：*在我前面*。
- `dot == 0` —— 垂直。*正侧方*，或者*在地平线上*。
- `dot < 0` —— 反向。*在我后面*。

光靠正负号就能回答一大票玩法问题：敌人在不在前面、玩家有没有面朝那扇门、这个表面朝向太阳吗。

## 它出现的四个地方

### 1. 光照 —— `dot(N, L)`

`N` 是表面法线（表面朝的方向），`L` 是指向光源的方向。表面正对光时 `dot(N, L)` 是 1，全亮；
背对光时是负数，而表面不可能被背面来光照亮：

```hlsl
float ndl = saturate(dot(N, L));          // 夹到 0..1
float3 lit = albedo * ndl * lightColor;   // Lambert
```

`saturate` 正是光照在背面不会「先变黑再变亮」的原因。这一行几乎是所有受光着色器的核心。

### 2. 朝向判断 —— `dot(forward, toTarget) > 0`

目标在我前面还是后面？不用 `Atan2`、不算角度，一次点乘。同一招也能回答「玩家有没有在看那扇门」
和「这个 AI 该不该注意到玩家」。

### 3. 投影 —— 这次移动有多少是往前的

以 `velocity` 移动，其中有多少顺着 `forward`？`dot(velocity, forward)` 给出一个能和速度上限
直接比的数。这也是「横移时走慢一点」「顶着墙时没有前进速度」的写法来源。

### 4. 边缘光与菲涅尔 —— `1 - dot(N, V)`

`V` 是指向摄像机的方向。表面与视线越接近「侧对」，`dot(N, V)` 越接近 0，`1 - dot(N, V)`
越接近 1 —— 那正好是边缘光或菲涅尔高光发亮的边缘：

```hlsl
float rim = pow(1.0 - saturate(dot(N, V)), 4.0);
```

## 代码里

=== "C#（Unity）"

    ```csharp
    // 先归一化：Dot 对任意长度都能算，但只有单位向量才给出余弦。
    Vector3 toTarget = (target.position - transform.position).normalized;
    float facing = Vector3.Dot(transform.forward, toTarget);   // 1 正前，0 侧面，-1 正后

    if (facing > 0f)
    {
        // 目标位于世界的前半部分
    }
    ```

=== "着色器（HLSL）"

    ```hlsl
    float3 N = normalize(i.normalWS);
    float3 L = normalize(_MainLightPosition.xyz);
    float  ndl = saturate(dot(N, L));
    ```

!!! note "点乘与 `Vector3.Angle`"
    `Vector3.Angle(a, b)` 返回的是角度（0–180），内部用的就是点乘。只需要比较 ——
    *在不在前面*、*在不在 45 度以内* —— 就直接用点乘：`dot > 0.707` 等价于「45 度以内」，
    不花三角函数。需要显示或插值这个数的时候，再拿 `Angle`。

## 三个坑

!!! danger "坑 1 —— 忘了归一化"
    `toTarget` 长度是 4 时，正对着它 `dot(forward, toTarget)` 返回 4。`> 0` 判断照样成立，
    所以 bug 藏得住 —— 直到代码开始和 `0.5` 这样的阈值比较。

!!! danger "坑 2 —— 把点乘当成角度"
    点乘 0.5 是 **60 度**，不是 0.5 度，也不是 30 度。要角度就取 `acos`；但只要做判断，
    就不要取。

!!! danger "坑 3 —— 混用坐标空间"
    **物体空间**的法线去点乘**世界空间**的光照方向，得到的是一个错的数，但它在表面上仍然平滑
    变化，所以看起来像光照。这就是经典的「阴影跟着模型一起转」bug。法线贴图为什么是蓝色，也是
    同一件事 —— 见[着色器里发生了什么](../shaders/what-happens-in-a-shader.md)。

## 自检

??? question "1. 两个单位向量的点乘是 0，夹角是多少？"
    90 度。单位向量的点乘就是 `cos(theta)`，而 `cos(90°) = 0`。

??? question "2. 球面上有一半 `dot(N, L)` 是负数。为什么那里的光照不会变成负的？"
    因为 `saturate`（夹到 0–1）。负值出现在背面，那里没有光；夹住之后是黑色，而不是「减掉光」。

??? question "3. 代码里写 `if (Vector3.Dot(transform.forward, toTarget) > 0.7f)`，实际条件是什么？"
    0.7 大约是 45 度的余弦，所以是「目标在正前方约 45 度以内」。如果 `toTarget` 没归一化，
    这个阈值的意思就完全变了。

??? question "4. 网格法线本来就是单位长度，为什么着色器里还要 `normalize(N)`？"
    因为三角形内部的插值会让它变短：两个单位向量的平均值几乎不会是单位长度。逐片元归一化，
    才让 `dot(N, L)` 真的是余弦。
